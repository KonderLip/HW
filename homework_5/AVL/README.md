# Задача 3. AVL

## 1. Объяснение решения

AVL-дерево — это BST, в котором после **каждой** операции для любого узла `x` выполняется инвариант:

$$|h(x.\text{left}) - h(x.\text{right})| \le 1$$

где `h` — высота поддерева (у пустого `0`, у листа `1`). Из этого следует, что высота всего дерева не превосходит
`1.44 · log₂(n + 2)`, и все операции остаются `O(log n)`.

Голый BST этого не гарантирует: при вставке отсортированных ключей он выродится в линию высоты `n`, и `search` станет
`O(n)`. AVL борется с этим **поворотами**, которые восстанавливают баланс после каждой модификации.

### Высота в узле

Высота хранится в каждом узле (`node.height`), а не вычисляется обходом поддерева. Иначе каждый `_balance_factor` был бы
`O(size)`, и вся выгода от балансировки пропала бы. При изменении детей высота пересчитывается за `O(1)`:

```python
def _update(node):
    node.height = 1 + max(_height(node.left), _height(node.right))
```

### Повороты

Поворот — локальная перестройка из трёх узлов, которая сохраняет BST-порядок и меняет высоты. Всего четыре случая, но
код сведён к двум примитивам — `_rotate_left` и `_rotate_right`, а `_rebalance` выбирает между ними по знаку
`balance_factor = h(left) − h(right)` и по знаку BF у ребёнка:

```python
def _rebalance(node):
    _update(node)
    bf = _balance_factor(node)
    if bf > 1:  # перевес слева
        if _balance_factor(node.left) < 0:  # LR
            node.left = _rotate_left(node.left)
        return _rotate_right(node)  # LL
    if bf < -1:  # перевес справа
        if _balance_factor(node.right) > 0:  # RL
            node.right = _rotate_right(node.right)
        return _rotate_left(node)  # RR
    return node
```

### Вставка

Обычный спуск BST: `<` — влево, `>` — вправо, `==` — ничего. Ключевое — что происходит **на возврате из рекурсии**.
После того как ребёнок вставлен, высота текущего узла могла измениться, и `_rebalance` пересчитывает её, проверяет BF и
при необходимости крутит. Поворот возвращает новый корень поддерева, который присваивается родителю.

```python
def _insert(self, node, key):
    if node is None:
        return Node(key)
    if key < node.key:
        node.left = self._insert(node.left, key)
    elif key > node.key:
        node.right = self._insert(node.right, key)
    else:
        return node  # дубликат
    return _rebalance(node)
```

Почему этого достаточно: любое нарушение баланса после вставки одного ключа имеет «свежий» характер — оно возникает
только на пути от корня к новому листу и только в тех узлах, где BF стал `±2`. Один поворот в первом таком узле (снизу
вверх) восстанавливает баланс на всём пути, потому что высота поддерева возвращается к прежней. Поэтому достаточно
одного прохода `_rebalance` на каждом уровне.

### Удаление

Три случая для узла `x` с ключом `key`:

- **`x` — лист** — просто отрезаем.
- **у `x` один ребёнок** — вместо `x` подставляем этого ребёнка.
- **у `x` два ребёнка** — находим **in-order successor** (минимум правого поддерева), копируем его ключ в `x`, затем
  физически удаляем successor из правого поддерева. У successor гарантированно нет левого ребёнка, поэтому его удаление
  сводится к одному из первых двух случаев.

```python
succ = node.right
while succ.left is not None:
    succ = succ.left
node.key = succ.key
_, node.right = self._delete(node.right, succ.key)
```

Рекурсия на возврате тоже вызывает `_rebalance` на каждом узле. В отличие от вставки, удаление может потребовать *
*`O(log n)` поворотов** — высота поддерева может уменьшиться, и это нарушит баланс у нескольких предков по цепочке. Но
каждый поворот — `O(1)`, а их не больше `O(log n)`.

Флаг `found` возвращается отдельно от `node`, чтобы отличать «удалено» от «ключа не было» — иначе `delete` не мог бы
вернуть `bool`.

### Поиск

Никаких поворотов, просто спуск по BST-указателям:

```python
def search(self, key):
    cur = self.root
    while cur is not None:
        if key == cur.key:
            return True
        cur = cur.left if key < cur.key else cur.right
    return False
```

## 2. Оценка сложности

**Время:**

| Операция | Сложность  | Откуда                                                       |
|----------|:----------:|--------------------------------------------------------------|
| `search` | `O(log n)` | высота AVL ≤ 1.44·log₂(n+2), спуск по одному пути            |
| `insert` | `O(log n)` | спуск + `_rebalance` на каждом уровне, каждый — `O(1)`       |
| `delete` | `O(log n)` | спуск + `O(log n)` поворотов на обратном пути, каждый `O(1)` |

Почему `_rebalance` — `O(1)`: `_update` — два обращения к `height`, `_balance_factor` — одно, каждый поворот —
переприсваивание трёх указателей и два `_update`. Всё константно.

Почему поиск successor в `delete` не ломает сложность: successor ищется спуском влево в правом поддереве `node`. Его
глубина — `O(log n)` (ограничена высотой дерева). Затем рекурсивный `_delete` идёт от корня правого поддерева до
successor — тоже `O(log n)`. Итого `delete` = `O(log n)` спуск + `O(log n)` поиск successor + `O(log n)` рекурсивное
удаление + `O(log n)` rebalance = `O(log n)`.

**Дополнительная память:**

- Само дерево — `O(n)` (по одному `Node` на уникальный ключ).
- Стек рекурсии `_insert`/`_delete` — `O(log n)`, потому что глубина ограничена высотой.
- Все операции `search` — итеративные, дополнительной памяти не требуют.
- Повороты — `O(1)`, живут только на время одного кадра.

**Замечание про высоту.** AVL-инвариант даёт `h ≤ 1.44·log₂(n+2)`. Это чуть хуже, чем у красно-чёрного дерева (
`2·log₂(n+1)` — то есть КЧ-деревья могут быть выше), но AVL строже балансирует, поэтому `search` в среднем быстрее за
счёт меньшей высоты. Плата — больше поворотов при модификациях.

## 3. Визуализация работы алгоритма

### Четыре случая дисбаланса

Каждый случай возникает после вставки одного ключа и требует своего набора поворотов. Обозначим
`bf(x) = h(left) − h(right)`.

#### LL — перевес влево-влево

Вставка `30, 20, 10`. У корня `bf = 2`, у `20` `bf = 1` (левый перевес, ребёнок тоже с левым перевесом). Один правый
поворот на `30`:

```
        30                       20
       /                        /  \
      20           →           10    30
     /
    10
```

#### RR — перевес вправо-вправо

Вставка `10, 20, 30`. Зеркально: один левый поворот на `10`:

```
    10                            20
      \                          /  \
       20           →           10    30
         \
          30
```

#### LR — перевес влево, ребёнок перевешен вправо

Вставка `30, 10, 20`. У корня `bf = 2` (левый перевес), но у `10` `bf = −1` (правый перевес). Один правый поворот не
поможет — `20` уйдёт влево и снова перекосит. Нужны **два** поворота: сначала левый на `10`, затем правый на `30`:

```
        30              30                  20
       /               /                   /  \
      10       →      20          →       10    30
        \            /
         20         10
```

#### RL — перевес вправо, ребёнок перевешен влево

Вставка `10, 30, 20`. Зеркально: правый поворот на `30`, затем левый на `10`:

```
    10                  10                    20
      \                   \                  /  \
       30       →          20       →      10    30
      /                      \
     20                       30
```

### Вставка в растущее дерево

Начнём с пустого и вставим `50, 30, 70, 20, 40, 60, 80`. Первые шесть вставок не требуют поворотов:

```
      50              50              50              50
     /               /  \            /  \            /  \
    30              30   70         30   70         30   70
                                   /               /  \
                                  20              20   40
```

Все BF в пределах `±1`. Добавим `60`:

```
           50
          /  \
        30    70
       /  \  /
      20  40 60
```

BF у `50` = `h(30) − h(70) = 2 − 2 = 0`, у `30` = `1 − 1 = 0`, у `70` = `1 − 0 = 1`. Всё ещё сбалансировано.

Добавим `80`:

```
           50
          /  \
        30    70
       /  \  /  \
      20  40 60  80
```

Полное дерево высоты 3, все BF ≤ 1.

Добавим `10`:

```
           50
          /  \
        30    70
       /  \  /  \
      20  40 60  80
     /
    10
```

Проверим BF снизу вверх: у `20` = `1 − 0 = 1`, у `30` = `2 − 1 = 1`, у `50` = `3 − 2 = 1`. Всё в порядке, поворотов не
нужно — это важный пример: **вставка не обязательно ломает баланс**, AVL не крутит дерево «на всякий случай».

Теперь добавим `5`:

```
           50
          /  \
        30    70
       /  \  /  \
      20  40 60  80
     /
    10
   /
  5
```

BF у `20` = `2 − 0 = 2` → нарушение. Смотрим на ребёнка `10`: у него BF = `1 − 0 = 1`, значит это **LL-случай**. Один
правый поворот на `20`:

```
           50
          /  \
        30    70
       /  \  /  \
      10  40 60  80
     /  \
    5   20
```

После поворота высота поддерева `10` стала 2 (было 3 у `20`), и BF у `30` = `2 − 1 = 1`, у `50` = `3 − 2 = 1`. Баланс
восстановлен, поворот остановился на первом же узле — это и есть «свежее» нарушение: достаточно одного поворота.

### Удаление узла с двумя детьми

Возьмём дерево:

```
           50
          /  \
        30    70
       /  \  /  \
      20  40 60  80
```

Удаляем `50`. У него два ребёнка, поэтому:

**Шаг 1.** Ищем successor — минимум правого поддерева. Спускаемся от `70` влево до упора: `70 → 60`. Successor = `60`.

**Шаг 2.** Копируем ключ `60` в `50`:

```
           60
          /  \
        30    70
       /  \  /  \
      20  40 60  80
```

Обратите внимание: **структура та же**, изменился только ключ в корне. BST-свойство сохранилось: `30 < 60 < 70`.

**Шаг 3.** Физически удаляем узел `60` из правого поддерева. У него нет детей, это лист:

```
           60
          /  \
        30    70
       /  \     \
      20  40    80
```

Проверим баланс: BF у `60` = `2 − 2 = 0`, у `70` = `0 − 1 = −1`, у `30` = `1 − 1 = 0`. Всё сбалансировано, поворотов не
нужно.

Здесь видно, почему удаление **может** потребовать `O(log n)` поворотов, а не одного: если бы удаляемый ключ был в более
глубоком узле, высота поддерева могла уменьшиться на 1 — и это нарушило бы баланс у каждого предка на пути вверх. Каждый
такой предок проверяется отдельно в `_rebalance`, а поскольку BF может скакнуть с `±1` до `±2` на нескольких уровнях
подряд, поворотов может быть много.

### Поиск

Никаких изменений структуры — просто спуск. Поиск `40` в дереве выше:

```
           60
          /  \
        30    70
       /  \     \
      20  40    80

шаг 1: 40 < 60 → влево к 30
шаг 2: 40 > 30 → вправо к 40
шаг 3: 40 == 40 → найдено
```

Три сравнения на дереве из шести узлов — это `⌈log₂ 6⌉ + 1 = 3`. В вырожденном BST из тех же ключей (
`20 → 30 → 40 → 60 → 70 → 80`) понадобилось бы до шести шагов. Ровно за это и платят поворотами при вставке и удалении.
