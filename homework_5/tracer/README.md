# Задача 1. Tracer

## 1. Объяснение решения

Декоратор — это функция, которая принимает другую функцию и возвращает её обёртку. Внутри обёртки мы можем делать что
угодно **до** и **после** вызова: здесь — печатать вход, увеличивать счётчик глубины, вызывать исходную функцию,
печатать выход (или исключение) и счётчик уменьшать.

### Счётчик глубины

Главная задача — на каждом уровне рекурсии печатать отступ, пропорциональный текущей глубине. Нужна переменная, которая:

- увеличивается на 1 при входе в функцию,
- уменьшается на 1 при выходе (в том числе при исключении),
- **одна на все задекорированные функции** — иначе при взаимной рекурсии (`f` вызывает `g`, `g` вызывает `f`) отступы
  будут прыгать, потому что у каждой обёртки свой счётчик.

Глобальная переменная (`global _depth`) эту задачу решает, но ломается в двух сценариях:

- **Потоки.** Два потока одновременно вызовут `f`, и счётчики перепутаются — у одного отступ будет на 2 больше, чем
  должен.
- **`asyncio`.** Все корутины работают в одном потоке, значит `threading.local` тоже не спасёт. Две задачи,
  пересекающиеся на `await`, видят одно и то же значение.

`contextvars.ContextVar` решает оба сценария. Каждый поток и каждая `asyncio.Task` получают **свой** контекст, а
`ContextVar` хранит значение «на контекст». Снаружи это выглядит как обычная переменная, но при переключении
потоков/задач её значение автоматически изолируется.

```python
_depth = contextvars.ContextVar("trace_depth", default=0)
```

`default=0` избавляет от проверки «а установлено ли значение» — до первого `set` `.get()` вернёт `0`, что для счётчика
глубины и есть правильное начальное состояние.

### `set` + `reset(token)`

```python
token = _depth.set(d + 1)
try:
    result = func(*args, **kwargs)
finally:
    _depth.reset(token)
```

`set` возвращает `token` — объект-«чек», который помнит предыдущее значение и контекст. `reset(token)` восстанавливает
это значение. Пара `set`/`reset` — идиоматический способ: `token` гарантирует, что откат вернёт именно то, что было до
нашего `set`, даже если внутри `func` кто-то (или сама `func`) ещё менял переменную. Он же защищает от двойного
использования — повторный `reset` бросит `RuntimeError`, что помогает ловить баги.

Можно было бы написать `_depth.set(d)` с сохранённым заранее `d`. В текущем коде это работало бы, но `reset(token)`
надёжнее: не требует, чтобы вы помнили старое значение, и корректно работает с вложенными `set` в чужом коде.

`reset` в `except`-блоке стоит **до** `print` — иначе отступ у строки `!!` окажется на уровень больше, чем у
соответствующей строки `->`.

### Формат вывода

- `-> name(args)` — вход, на текущей глубине.
- `<- name(args) = result` — нормальный возврат, на той же глубине.
- `!! name raised Type: msg` — исключение, на той же глубине.

Символы `->` / `<-` / `!!` визуально образуют дерево вызовов: входы идут вниз, выходы — вверх, исключения отмечают
ветку, которая не завершилась нормально.

Аргументы и результат печатаются через `repr` (`!r` в f-строке), а не через `str`. Для строк это критично: `f("hello")`
в логе выглядит как `-> f('hello')` — сразу видно, что это строка, а не имя переменной. Для контейнеров `str` и `repr`
дают одинаковый результат, но `repr` — правильный выбор по умолчанию для отладочного вывода.

### `functools.wraps`

```python
@functools.wraps(func)
def wrapper(*args, **kwargs):
    ...
```

Без этого декоратор сломал бы интроспекцию: `f.__name__` стал бы `"wrapper"`, `f.__doc__` потерялся бы,
`inspect.signature(f)` показал бы `(*args, **kwargs)` вместо реальной сигнатуры. `functools.wraps` копирует метаданные
исходной функции и выставляет `__wrapped__`, через который можно добраться до оригинала (`f.__wrapped__` — это исходный
`func`).

### Обработка исключений

```python
except BaseException as e:
_depth.reset(token)
print(f"{indent}!! {func.__name__} raised {type(e).__name__}: {e}")
raise
```

`BaseException`, а не `Exception`: `KeyboardInterrupt`, `SystemExit` тоже должны приводить к корректному откату `_depth`
и к печати, иначе после Ctrl-C счётчик останется неверным. `raise` без аргументов пробрасывает **то же самое**
исключение дальше с сохранением traceback — это важно, `raise e` потерял бы оригинальную точку возбуждения.

`_depth.reset(token)` вызывается **до** `print` — чтобы отступ у строки `!!` совпадал с отступом у соответствующей
строки `->`.

## 2. Оценка сложности

**Время:** `O(1)` на каждый вызов функции сверх времени самой функции, но с оговоркой про длину отступа.

- `_depth.get()` — `O(1)`.
- `_depth.set` / `_depth.reset` — `O(1)`.
- Построение `args_repr`: `O(k)` на `k` аргументов, каждый `repr` — своя стоимость (зависит от типа).
- Построение отступа `"  " * d` — `O(d)`, где `d` — глубина.
- `print` — `O(d + |args_repr| + |result_repr|)`.

Итого на вызов — `O(k + d + |args| + |result|)`. Для рекурсии глубины `d` полное время трассировки — сумма по всем
вызовам:

$$T_{\text{trace}} = O\!\left(\sum_{i=0}^{d} (k + i + |\text{args}_i| + |\text{result}_i|)\right)$$

Квадратичный член `Σ i = O(d²)` — это плата за отступы: на глубине `d` печатается `2d` пробелов. Для учебной задачи (`d`
обычно до десятков) это несущественно, но стоит помнить: **сама трассировка — не `O(1)` на вызов, а `O(d)` из-за отступа
**.

**Дополнительная память:** `O(1)` на вызов сверх того, что занимает сама рекурсия.

- `token`, `d`, `indent`, `args_repr`, `result` — всё локальные переменные одного кадра, `O(1)` каждая.
- `ContextVar` хранит одно `int` на контекст, не на вызов.
- Строки, которые строятся для `print`, — временные, освобождаются сразу.

Общая память на всю программу — `O(d)` из-за стека вызовов, но это заслуга самой рекурсии, а не декоратора.

## 3. Визуализация работы алгоритма

Возьмём классическую рекурсию:

```python
@tracer
def fact(n):
    if n <= 1:
        return 1
    return n * fact(n - 1)
```

Вызов `fact(3)`. Проследим за `_depth` и стеком вызовов.

### Состояние `_depth` по шагам

| Шаг | Действие               | `d` до | `_depth` после | Что печатается       |
|:---:|------------------------|:------:|:--------------:|----------------------|
|  1  | вход `fact(3)`         |   0    |       1        | `-> fact(3)`         |
|  2  | вход `fact(2)`         |   1    |       2        | `  -> fact(2)`       |
|  3  | вход `fact(1)`         |   2    |       3        | `    -> fact(1)`     |
|  4  | `fact(1)` возвращает 1 |   3    |       2        | `    <- fact(1) = 1` |
|  5  | `fact(2)` возвращает 2 |   2    |       1        | `  <- fact(2) = 2`   |
|  6  | `fact(3)` возвращает 6 |   1    |       0        | `<- fact(3) = 6`     |

Обратите внимание на шаги 4–6: `reset(token)` выполняется **до** `print`, поэтому `d` для `<-` берётся уже уменьшенное —
и отступ у `<-` совпадает с отступом у парного `->`.

### Стек вызовов и вывод

Стек растёт до самого дна (`fact(1)`), затем сворачивается:

```
стек:  [fact(3)]        — _depth=1
вывод: -> fact(3)

стек:  [fact(3), fact(2)]        — _depth=2
вывод: -> fact(3)
         -> fact(2)

стек:  [fact(3), fact(2), fact(1)]        — _depth=3
вывод: -> fact(3)
         -> fact(2)
           -> fact(1)

стек:  [fact(3), fact(2)]        — _depth=2
вывод: -> fact(3)
         -> fact(2)
           -> fact(1)
           <- fact(1) = 1

стек:  [fact(3)]        — _depth=1
вывод: -> fact(3)
         -> fact(2)
           -> fact(1)
           <- fact(1) = 1
         <- fact(2) = 2

стек:  []        — _depth=0
вывод: -> fact(3)
         -> fact(2)
           -> fact(1)
           <- fact(1) = 1
         <- fact(2) = 2
       <- fact(3) = 6
```

### Взаимная рекурсия

Главное, зачем нужен общий `ContextVar`: `is_even` и `is_odd` вызывают друг друга.

```python
@tracer
def is_even(n):
    if n == 0:
        return True
    return is_odd(n - 1)


@tracer
def is_odd(n):
    if n == 0:
        return False
    return is_even(n - 1)


is_even(3)
```

Вывод:

```
-> is_even(3)
  -> is_odd(2)
    -> is_even(1)
      -> is_odd(0)
      <- is_odd(0) = False
    <- is_even(1) = False
  <- is_odd(2) = False
<- is_even(3) = False
```

Если бы у каждой обёртки был свой счётчик, `is_odd(2)` начал бы с отступа 0 (потому что для `is_odd` это первый вызов),
и структура дерева вызовов визуально разрушилась бы. Общий `ContextVar` сохраняет глубину независимо от того, **какая
именно** функция вызывается.

### Исключение в глубине

```python
@tracer
def rec(n):
    if n == 0:
        raise ValueError("bottom")
    return rec(n - 1)


rec(2)
```

Вывод:

```
-> rec(2)
  -> rec(1)
    -> rec(0)
    !! rec raised ValueError: bottom
  !! rec raised ValueError: bottom
!! rec raised ValueError: bottom
```

Каждый уровень печатает `!!` **на своём отступе** — потому что `reset(token)` стоит до `print`. И каждый пробрасывает
исключение через `raise`, поэтому верхние уровни тоже его видят. В конце контекст `ContextVar` возвращается к 0:
следующий вызов `rec` начнётся с отступа 0, а не с 3.
