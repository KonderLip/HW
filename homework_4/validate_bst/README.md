# Задача 2. Validate BST

## 1. Объяснение решения

### Что значит «быть BST»

Бинарное дерево является BST, если для **каждого** узла `x` выполнено:

$$\max(\text{keys in } x.\text{left}) < x.\text{key} < \min(\text{keys in } x.\text{right})$$

(для пустого поддерева соответствующая граница — это `±∞`).

Важно, что это условие **глобальное**: оно про **все** ключи поддерева, а не только про непосредственного ребёнка.
Классический контрпример — дерево

```
       5
      / \
     3   8
        /
       7
      /
     4
```

У каждой пары родитель–ребёнок локально всё хорошо: `3 < 5`, `8 > 5`, `7 < 8`, `4 < 7`. Но `4` лежит в правом поддереве
`5` и потому обязано быть `> 5`. Проверка «сравнить с прямыми детьми» даст `True`, а правильный ответ — `False`.

### Почему `max(left) < key < min(right)` равносильно прокидыванию границ

Условие BST для узла `x` записывается через `max`/`min`, но у него есть эквивалентная формулировка **без** `max`/`min`:

$$\max(x.\text{left}) < x.\text{key} \;\Longleftrightarrow\; \forall\, y \in x.\text{left}:\; y.\text{key} < x.\text{key}$$

$$\min(x.\text{right}) > x.\text{key} \;\Longleftrightarrow\; \forall\, z \in x.\text{right}:\; z.\text{key} > x.\text{key}$$

То есть «максимум слева меньше `x.key`» — это то же самое, что «**каждый** узел слева меньше `x.key`». То же зеркально
справа.

Спускаясь от `x` к левому ребёнку `L`, мы передаём `upper = x.key`. Внутри поддерева `L` каждый узел будет проверен на
`key < upper = x.key`. Это и есть разложение универсального квантора `∀ y ∈ x.left: y < x.key` на **индивидуальные
проверки** для каждого потомка слева. Аналогично `lower = x.key` при спуске вправо разворачивает
`∀ z ∈ x.right: z > x.key` в проверки `z > lower` для каждого узла справа.

Ключевой момент: `x` — не единственный, кто накладывает ограничение. Если `x` сам лежит в левом поддереве предка `p`, то
`p` наложил на всё поддерево `x` ограничение `key < p.key`. При спуске от `p` к `x` это ограничение уже лежит в `upper`.
Значит, границы `(lower, upper)` в узле — это **накопленные** ограничения от всех предков, а не только от
непосредственного родителя. Проверка `lower < x.key < upper` в каждом узле в совокупности даёт `∀ y ∈ x.left: y < x.key`
и `∀ z ∈ x.right: z > x.key` для **каждого** `x`.

Именно это делает алгоритм линейным: `max`/`min` для поддеревьев нигде явно не вычисляются, они «собираются» из
уточнений границ вдоль пути от корня.

### DFS и разворот рекурсии в стек

Рекурсивная версия:

```python
def dfs(node, lower, upper):
    if node is None:
        return True
    if not (lower < node.key < upper):
        return False
    return dfs(node.left, lower, node.key) and dfs(node.right, node.key, upper)
```

Рекурсию можно развернуть в явный стек, храня на каждом шаге тройку `(node, lower, upper)`. Стек работает по LIFO;
порядок обхода — pre-order (сначала проверяем узел, потом пушим детей), что и нужно, потому что проверка условия
`lower < key < upper` локальна для узла и не требует, чтобы дети были обработаны раньше.

## 2. Оценка сложности

**Время: `O(n)`**, где `n` — число узлов.

- Каждый реальный узел кладётся в стек ровно один раз и снимается ровно один раз.
- На каждом снятии — одна проверка `lower < key < upper` и до двух `append` для детей.
- Все операции — `O(1)`, итого `O(n)`.

**Дополнительная память: `O(h)`**, где `h` — высота дерева.

- Стек в любой момент содержит узлы «фронта» обхода: путь от корня к текущему плюс отложенные правые поддеревья. Это
  `O(h)`.
- В худшем случае (дерево-линия) `h = n`, память `O(n)`. В лучшем (полное) `h = log n`, память `O(log n)`.

Обратите внимание на разницу с наивным подходом, который для каждого узла явно ищет `max`/`min` в поддереве: тот был бы
`O(n²)`. Прокидывание границ убирает это — `max`/`min` для поддерева «вычисляются» неявно, через последовательность
уточнений интервала вдоль пути от корня.

## 3. Визуализация работы алгоритма

### Валидное дерево

```
        5
       / \
      3   8
     / \   \
    2   4   9
```

Пройдём итеративно. `L`/`U` — границы, `ok` — прошла ли проверка `L < key < U`.

| Шаг | pop `(node, L, U)` |  `L < key < U`  | push                       |
|:---:|--------------------|:---------------:|----------------------------|
|  1  | `(5, -∞, +∞)`      | `-∞ < 5 < +∞` ✓ | `(8, 5, +∞)`, `(3, -∞, 5)` |
|  2  | `(3, -∞, 5)`       | `-∞ < 3 < 5` ✓  | `(4, 3, 5)`, `(2, -∞, 3)`  |
|  3  | `(2, -∞, 3)`       | `-∞ < 2 < 3` ✓  | —                          |
|  4  | `(4, 3, 5)`        |  `3 < 4 < 5` ✓  | —                          |
|  5  | `(8, 5, +∞)`       | `5 < 8 < +∞` ✓  | `(9, 8, +∞)`               |
|  6  | `(9, 8, +∞)`       | `8 < 9 < +∞` ✓  | —                          |

Все проверки прошли → `True`. Обратите внимание, как **сужаются** границы при спуске: у узла `4` интервал `(3, 5)`,
потому что он в левом поддереве `5` (даёт `U = 5`) и в правом поддереве `3` (даёт `L = 3`).

### Невалидное дерево — тот самый контрпример

```
       5
      / \
     3   8
        /
       7
      /
     4
```

| Шаг | pop `(node, L, U)` | `L < key < U` | push                       |
|:---:|--------------------|:-------------:|----------------------------|
|  1  | `(5, -∞, +∞)`      |       ✓       | `(8, 5, +∞)`, `(3, -∞, 5)` |
|  2  | `(3, -∞, 5)`       |       ✓       | —                          |
|  3  | `(8, 5, +∞)`       |       ✓       | `(7, 5, 8)`                |
|  4  | `(7, 5, 8)`        | `5 < 7 < 8` ✓ | `(4, 5, 7)`                |
|  5  | `(4, 5, 7)`        |   `5 < 4` ✗   | —                          |

На шаге 5 видно, откуда берётся `lower = 5`: узел `4` лежит в правом поддереве `5`, а спуск к `4` прошёл через правого
ребёнка `5` (это дало `L = 5`), затем налево к `8`, затем налево к `7`, затем налево к `4` (это дало `U = 7`). Интервал
`(5, 7)` — точное условие, которому `4` обязано удовлетворять, чтобы быть BST. Оно нарушено → `False`.

### Порядок в стеке

Стек на шаге 1 после обработки корня (верхушка **справа**):

```
stack = [ (8, 5, +∞), (3, -∞, 5) ]
```

Правый ребёнок лежит **ниже** левого, потому что мы пушим его первым. LIFO гарантирует, что левое поддерево полностью
обработается до правого. Это не влияет на корректность (порядок обхода pre-order неважен для проверки каждого узла в
отдельности), но объясняет, почему на шагах 2–4 мы уходим в левое поддерево, а к правому возвращаемся только на шаге 5.
