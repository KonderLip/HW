# Задача 2. Iterative

## 1. Объяснение решения

Задача — реализовать **итеративные** версии mergesort и quicksort. Логика самих алгоритмов не меняется: `_merge` и
`_partition` остаются теми же функциями, что в рекурсивных версиях. Меняется только способ обхода дерева рекурсии —
вместо стека вызовов используется явный стек (для quicksort) или порядок обхода снизу вверх (для mergesort).

### Mergesort: bottom-up

Рекурсивный mergesort строит дерево сверху вниз: делит массив пополам, рекурсивно сортирует половины, сливает.
Итеративная версия идёт по **уровням** этого дерева **снизу вверх**:

```python
width = 1
while width < n:
    lo = 0
    while lo < n:
        mid = min(lo + width, n)
        hi = min(lo + 2 * width, n)
        if mid < hi and result[mid - 1] > result[mid]:
            _merge(result, buf, lo, mid, hi)
        lo += 2 * width
    width *= 2
```

- **`width = 1`** — сливаем пары одиночных элементов, получаем блоки по 2.
- **`width = 2`** — сливаем пары блоков по 2, получаем блоки по 4.
- **`width = 4`** — блоки по 8.
- И так до `width ≥ n`.

Внешний цикл — `log₂ n` итераций (уровни дерева). Внутренний — `O(n / width)` итераций на уровне. Суммарно `O(n)` работы
на уровень, `O(n log n)` — итого.

Две детали, которых нет в рекурсивной версии:

- **`min(lo + width, n)` и `min(lo + 2 * width, n)`** — защита от выхода за границу. Когда `n` не степень двойки,
  последний блок на уровне может быть короче `width`. Без `min` получим `IndexError`.
- **Условие `result[mid - 1] > result[mid]`** — оптимизация «уже отсортировано». Если последний элемент левой половины
  не больше первого элемента правой, сливать нечего. На отсортированном входе `_merge` не вызывается ни на одном уровне,
  и время падает до `O(n)`. Точно та же проверка есть в рекурсивной версии.

Никакой рекурсии — только два вложенных `while`. Стек рекурсии не используется вообще, поэтому глубина стека `O(1)`
независимо от `n`.

### Quicksort: явный стек диапазонов

Рекурсивный quicksort вызывает себя дважды: `_qs(lo, p+1)` и `_qs(p+1, hi)`. Итеративная версия кладёт эти диапазоны в
явный стек `(lo, hi)` и обрабатывает, пока стек не пуст:

```python
stack = [(0, n)]
while stack:
    lo, hi = stack.pop()
    if hi - lo <= 1:
        continue
    p = _partition(result, lo, hi, rng)

    left_size = p + 1 - lo
    right_size = hi - (p + 1)
    if left_size < right_size:
        if p + 1 < hi:
            stack.append((p + 1, hi))
        if lo < p + 1:
            stack.append((lo, p + 1))
    else:
        if lo < p + 1:
            stack.append((lo, p + 1))
        if p + 1 < hi:
            stack.append((p + 1, hi))
```

`_partition` — Hoare с random pivot, ровно та же, что в рекурсивной версии. Возвращает `p ∈ [lo, hi−2]`, и рекурсия идёт
по `[lo, p+1)` и `[p+1, hi)` — **`a[p]` уже на своём месте**, повторно его не обрабатываем.

**Ключевая деталь — порядок push.** Наивно можно написать:

```python
stack.append((lo, p + 1))
stack.append((p + 1, hi))
```

Это работает, но стек может вырасти до **`O(n)`**. Причина: `pop` берёт последний элемент, значит обрабатывается 
**правая** половина, а левая лежит в стеке. Если pivot всегда попадает в край (killer-последовательность или специально
подобранный вход), левая половина имеет размер 1, правая — `n − 1`, и каждый следующий уровень снова откладывает в стек
диапазон размера `n − 2`, `n − 3`, и т.д. Стек линейный.

Трюк «**push larger half first, smaller half second**» это чинит. `pop` берёт последний элемент — меньшую половину.
Значит, следующая итерация работает с **меньшей** половиной. Размер активного диапазона уменьшается **как минимум вдвое
** на каждом шаге. Отложенная большая половина может понадобиться позже, но каждая отложенная часть ограничена
`n/2, n/4, n/8, …` от исходного размера — их суммарное число `O(log n)`.

Итог: **глубина стека ≤ 2 · log₂ n** даже в худшем случае. С random pivot худший случай и так маловероятен, а с этим
трюком — **структурно** не приводит к линейному стеку.

**Проверки `p + 1 < hi` и `lo < p + 1`** — защита от пуша пустых диапазонов. `_partition` возвращает `j ∈ [lo, hi−2]`,
значит `lo < p+1` всегда (левая часть непустая), а `p+1 = hi` возможно (правая пустая). Без проверки мы бы просто пушили
пустой диапазон и отсеивали его на `pop` через `if hi - lo <= 1: continue` — код работал бы, но делал бы лишние
`push/pop`.

### Что общего с рекурсивными версиями

- **`_merge` и `_partition` идентичны** — они и не рекурсивные, поэтому менять их не нужно. Это ключевой момент:
  итеративность достигается только заменой обхода дерева, а не переписыванием работы на узле.
- **`buf` в mergesort и `stack` в quicksort** — аналоги стека вызовов. У mergesort это **один буфер на всё дерево** (
  потому что bottom-up не нужно хранить промежуточные состояния между уровнями), у quicksort — **список диапазонов** (
  потому что порядок обхода произвольный).
- **Random pivot и stability** — наследуются от рекурсивных версий. Quicksort так же нестабилен, mergesort так же
  стабилен (`<=` при слиянии).

## 2. Оценка сложности

### Mergesort

**Время:**

- Внешний цикл `while width < n` — `⌈log₂ n⌉` итераций.
- Внутренний цикл на уровне `width` — `⌈n / (2·width)⌉` итераций, каждая — `O(width)` работы по слиянию.
- Суммарно на уровне — `O(n)`, итого `O(n log n)`.

С short-circuit `result[mid - 1] > result[mid]`:

- **Отсортированный вход:** условие ложно на каждом уровне, `_merge` не вызывается → `O(n)`.
- **Обратно отсортированный:** условие истинно на каждом уровне → `O(n log n)`.
- **Случайный:** `O(n log n)`.

**Дополнительная память:**

- Буфер `buf` — `O(n)`, создаётся один раз.
- Стек — **`O(1)`**. Рекурсии нет, только локальные переменные `width, lo, mid, hi, i, j, k`.
- Итого `O(n)` — на буфер.

**Стабильность:** да. `_merge` использует `<=` при равных ключах.

### Quicksort

**Время:**

- Средний случай: `O(n log n)` — ожидаемое число сравнений `~2n ln n` при random pivot.
- Худший случай: `O(n²)` — при крайне неудачных pivot'ах, но при random pivot вероятность падает экспоненциально.
- На массиве с дубликатами: `O(n log n)` благодаря Hoare.

**Дополнительная память:**

- Стек: **`O(log n)` гарантированно** благодаря «smaller half first». Без этого трюка было бы `O(n)` в худшем,
  `O(log n)` в среднем. С трюком — **`O(log n)` в худшем**.
- In-place: никаких вспомогательных массивов, сортировка на копии `result` (копия в `quicksort` — для не-мутации входа).

**Стабильность:** нет.

### Сравнение с рекурсивными версиями

| Свойство         | Mergesort рекурс. | Mergesort iter. | Quicksort рекурс. | Quicksort iter. |
|------------------|-------------------|-----------------|-------------------|-----------------|
| Время            | `O(n log n)`      | `O(n log n)`    | `O(n log n)`      | `O(n log n)`    |
| Стек             | `O(log n)`        | **`O(1)`**      | `O(n)` худший     | **`O(log n)`**  |
| Память           | `O(n)` буфер      | `O(n)` буфер    | `O(log n)`        | `O(log n)`      |
| `RecursionError` | возможен          | **невозможен**  | возможен          | **невозможен**  |

**Mergesort**: итеративная версия выигрывает в **памяти на стек** (`O(1)` вместо `O(log n)`) и не падает с
`RecursionError` при большом `n`. По времени — то же.

**Quicksort**: итеративная версия выигрывает в **худшем размере стека** (`O(log n)` вместо возможного `O(n)`) благодаря
трюку с меньшей половиной. Рекурсивная версия без этого трюка могла бы иметь `O(n)` глубину в плохом случае — и это уже
риск `RecursionError` на `n > 1000`. Итеративная — нет.

### Практические замечания

- **`O(1)` для стека mergesort** — это про **алгоритмическую** память. В Python есть некоторые накладные расходы на кадр
  `_merge`, но это `O(1)` от `n`.
- **`O(log n)` для стека quicksort** — это уже с трюком. Без него в худшем случае стек мог бы вырасти до `n` элементов,
  каждый — `tuple` из двух `int`. Для `n = 10⁶` это `~50 МБ` — заметно, но не критично. С трюком — `~20 элементов`,
  пренебрежимо.
- **`sys.setrecursionlimit(50)`** — мощный способ проверить, что решение **действительно итеративное**. Если внутри
  остался хоть один рекурсивный вызов, тест на `n = 10_000` сразу упадёт.

## 3. Визуализация работы алгоритма

### Mergesort: bottom-up обход дерева

Возьмём `[5, 2, 8, 1, 9, 3, 7, 4]`, `n = 8`.

Рекурсивный mergesort строит такое дерево (деление сверху вниз):

```
        [5, 2, 8, 1, 9, 3, 7, 4]            ← уровень 0
          /                  \
    [5, 2, 8, 1]        [9, 3, 7, 4]        ← уровень 1
      /      \            /      \
   [5, 2]  [8, 1]      [9, 3]  [7, 4]       ← уровень 2
   /  \    /  \        /  \    /  \
  [5][2]  [8][1]      [9][3]  [7][4]         ← уровень 3 (листья)
```

Bottom-up mergesort обходит это дерево **снизу вверх**, сливая узлы на каждом уровне:

**`width = 1`** — сливаем соседние одиночные элементы:

```
[5][2]  [8][1]  [9][3]  [7][4]
   ↓       ↓       ↓       ↓
 [2, 5]  [1, 8]  [3, 9]  [4, 7]
```

Массив: `[2, 5, 1, 8, 3, 9, 4, 7]`

**`width = 2`** — сливаем пары блоков по 2:

```
[2, 5]  [1, 8]      [3, 9]  [4, 7]
    ↓                   ↓
[1, 2, 5, 8]        [3, 4, 7, 9]
```

Массив: `[1, 2, 5, 8, 3, 4, 7, 9]`

**`width = 4`** — сливаем пару блоков по 4:

```
[1, 2, 5, 8]        [3, 4, 7, 9]
               ↓
    [1, 2, 3, 4, 5, 7, 8, 9]
```

Массив отсортирован.

На каждом уровне — одна и та же операция `_merge`, применённая к разным `(lo, mid, hi)`. Никакой рекурсии — только два
счётчика `width` и `lo`.

### Mergesort: обработка `n` не степень двойки

Возьмём `n = 5`, `[3, 1, 4, 1, 5]`. `n` не степень двойки, последний блок на некоторых уровнях короче `width`.

**`width = 1`**: `lo` пробегает `0, 2, 4`.

- `lo = 0`: `mid = min(1, 5) = 1`, `hi = min(2, 5) = 2` — сливаем `[3]` и `[1]` → `[1, 3]`
- `lo = 2`: `mid = min(3, 5) = 3`, `hi = min(4, 5) = 4` — сливаем `[4]` и `[1]` → `[1, 4]`
- `lo = 4`: `mid = min(5, 5) = 5`, `hi = min(6, 5) = 5` — **`mid == hi`, блок неполный, слияние пропускается**

Массив: `[1, 3, 1, 4, 5]`

**`width = 2`**: `lo` пробегает `0, 4`.

- `lo = 0`: `mid = min(2, 5) = 2`, `hi = min(4, 5) = 4` — сливаем `[1, 3]` и `[1, 4]` → `[1, 1, 3, 4]`
- `lo = 4`: `mid = min(6, 5) = 5`, `hi = min(8, 5) = 5` — **снова пропуск**

Массив: `[1, 1, 3, 4, 5]`

**`width = 4`**: `lo = 0`.

- `mid = min(4, 5) = 4`, `hi = min(8, 5) = 5` — сливаем `[1, 1, 3, 4]` и `[5]` → `[1, 1, 3, 4, 5]`

Готово. Именно `min(...)` и проверка `mid < hi` спасают от `IndexError` на неполных блоках.

### Quicksort: разбиение и явный стек

Возьмём `[5, 2, 8, 1, 9, 3, 7, 4]`, `n = 8`, pivot = 5 (для наглядности).

**Первый `_partition(0, 8)`:**

| Шаг | Действие                                                                       | Массив                     |
|:---:|--------------------------------------------------------------------------------|----------------------------|
|  1  | `i` доходит до `0` (`a[0]=5≥5`), `j` доходит до `7` (`a[7]=4≤5`). `i<j` → swap | `[4, 2, 8, 1, 9, 3, 7, 5]` |
|  2  | `i` до `2` (`a[2]=8≥5`), `j` до `5` (`a[5]=3≤5`). `i<j` → swap                 | `[4, 2, 3, 1, 9, 8, 7, 5]` |
|  3  | `i` до `4` (`a[4]=9≥5`), `j` до `3` (`a[3]=1≤5`). `i≥j` → стоп, return `j=3`   | —                          |

Результат: `[4, 2, 3, 1 | 9, 8, 7, 5]`, `p = 3`. Левая часть `[0, 4)`, правая `[4, 8)`. `left_size = 4, right_size = 4`.

Так как `left_size >= right_size` (не строго меньше), идём в `else`-ветку:

- `push(0, 4)` — левая половина
- `push(4, 8)` — правая половина

Стек: `[(0, 4), (4, 8)]`.

**`pop` → `(4, 8)`**. Обрабатываем правую половину `[9, 8, 7, 5]`, pivot = 8 (случайный):

`_partition(4, 8)` с pivot = 8:

- Начало: `i = 3, j = 8`
- `i` до `4` (`a[4]=9≥8`), `j` до `7` (`a[7]=5≤8`). `i<j` → swap `a[4]` и `a[7]` → `[4, 2, 3, 1, 5, 8, 7, 9]`
- `i` до `5` (`a[5]=8≥8`), `j` до `6` (`a[6]=7≤8`). `i<j` → swap `a[5]` и `a[6]` → `[4, 2, 3, 1, 5, 7, 8, 9]`
- `i` до `6` (`a[6]=8≥8`), `j` до `5` (`a[5]=7≤8`). `i≥j` → return `j=5`

Результат: `[4, 2, 3, 1, 5 | 7, 8, 9]`, `p = 5`. Левая часть `[4, 6)` размера 2, правая `[6, 8)` размера 2. Push в
порядке, зависящем от размера — обе равны, идём в `else`:

- `push(4, 6)` — левая (размер 2)
- `push(6, 8)` — правая (размер 2)

Стек: `[(0, 4), (4, 6), (6, 8)]`.

**`pop` → `(6, 8)`**, `_partition(6, 8)` для `[8, 9]`, pivot = 8:

- `i` до `6` (`a[6]=8≥8`), `j` до `6` (`a[6]=8≤8`). `i≥j` → return `j=6`

Результат: `p = 6`, левая `[6, 7)` размера 1, правая `[7, 8)` размера 1. Обе тривиальны (`hi-lo <= 1`), push не делает:

- `left_size = 1 < right_size = 1`? Нет, `else`-ветка.
- `if lo < p + 1`: `6 < 7` — да, `push(6, 7)`.
- `if p + 1 < hi`: `7 < 8` — да, `push(7, 8)`.

Стек: `[(0, 4), (4, 6), (6, 7), (7, 8)]`.

**`pop` → `(7, 8)`** — `hi - lo = 1`, `continue`. Стек: `[(0, 4), (4, 6), (6, 7)]`.

**`pop` → `(6, 7)`** — `hi - lo = 1`, `continue`. Стек: `[(0, 4), (4, 6)]`.

**`pop` → `(4, 6)`** — `[5, 7]`, `hi - lo = 2`. `_partition(4, 6)` с pivot = 5:

- `i = 3, j = 6`
- `i` до `4` (`a[4]=5≥5`), `j` до `5` (`a[5]=7>5`, `j` до `4` — `a[4]=5≤5`). `i≥j` → return `j=4`

`p = 4`, обе части размера 1. Push `(4, 5)` и `(5, 6)`. Стек: `[(0, 4), (4, 5), (5, 6)]`.

**`pop` → `(5, 6)`** — размер 1, `continue`. **`pop` → `(4, 5)`** — размер 1, `continue`.

**`pop` → `(0, 4)`** — `[4, 2, 3, 1]`, аналогично разбивается и обрабатывается. После всех итераций стек пуст, массив
отсортирован.

### Smaller-half-first в действии

Сравним два варианта на `n = 8` с pivot всегда в крайнем левом элементе (adversarial). Начало: `_partition(0, 8)`
возвращает `p = 0` (pivot = минимум, левая часть размера 1, правая размера 7).

**Наивный push (левая, правая):**

```python
stack.append((lo, p + 1))  # (0, 1) — размер 1
stack.append((p + 1, hi))  # (1, 8) — размер 7
```

Стек: `[(0, 1), (1, 8)]`. `pop` → `(1, 8)` — правая, размер 7. Обрабатываем. Снова `p = 1` (pivot = `a[1]` = минимум
оставшихся). Push `(1, 2)` и `(2, 8)`. Стек: `[(0, 1), (1, 2), (2, 8)]`. И так далее — **стек растёт линейно**, потому
что мы каждый раз берём **большую** часть и оставляем в стеке кучу маленьких.

**Smaller-half-first (в коде):**

```python
# left_size = 1 < right_size = 7 → правый стек первым
if p + 1 < hi:
    stack.append((p + 1, hi))  # (1, 8) — размер 7, откладываем
if lo < p + 1:
    stack.append((lo, p + 1))  # (0, 1) — размер 1, сверху
```

Стек: `[(1, 8), (0, 1)]`. `pop` → `(0, 1)` — **маленькая** часть. `continue` (размер 1). `pop` → `(1, 8)`. Обрабатываем,
`p = 1`. Push `(2, 8)` и `(1, 2)`. Стек: `[(2, 8), (1, 2)]`. `pop` → `(1, 2)` — размер 1, `continue`. `pop` → `(2, 8)`.
И так далее.

Стек в этом сценарии **не превышает 2 элементов** — потому что мы всегда обрабатываем меньшую часть сразу, а большая
откладывается и обрабатывается, только когда все меньшие части уже обработаны. Общее число отложенных больших частей —
`log₂ n` (каждая отложенная часть — это кусок, вдвое меньший предыдущего). Именно это даёт `O(log n)` вместо `O(n)`.

### Что было бы при `_partition` из Lomuto

Для контраста — если бы использовали Lomuto вместо Hoare, то на массиве `[7, 7, 7, 7, 7]` (все равны) Lomuto возвращает
`p = hi - 1` каждый раз (pivot отделяет 0 элементов меньше себя), и рекурсия идёт по размеру `n − 1` и `0`. Это `O(n²)`.
Hoare разносит равные элементы на обе стороны (`while a[i] < pivot` без `<=`), возвращает `p ≈ hi/2`, рекурсия идёт по
двум половинам. `O(n log n)`. Именно за это и выбирают Hoare в итеративной версии.
