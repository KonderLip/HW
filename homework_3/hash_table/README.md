# Задача 3. Создание хеш-таблицы

## Как устроена таблица

Таблица состоит из двух логических частей, размещённых в одном массиве `_data`:

```
Индексы:   0                primary_size-1 │ primary_size               primary_size+cellar_size-1
           ┌──────────────────────────────┐ ┌──────────────────────────────────────────┐
_data:     │       Основная область       │ │              Погреб (cellar)             │
           │   (address region)           │ │                                          │
           │   hash(key) % primary_size   │ │   сюда складываются элементы,            │
           │   указывает сюда             │ │   вызвавшие коллизию                     │
           └──────────────────────────────┘ └──────────────────────────────────────────┘
```

- **Основная область** (primary region) — сюда хеш-функция направляет ключи.
  Размер `primary_size_` — простое число из таблицы PRIMES.
- **Погреб** (cellar) — резервные слоты для разрешения коллизий. Хеш-функция
  сюда не адресует напрямую; элементы попадают сюда, когда их «родной» слот занят.
- Каждый слот (`_Data`) хранит: ключ, значение, флаги `used` / `deleted`
  и ссылку `next` — индекс следующего элемента в цепочке коллизий.

Когда ключ хешируется в занятый слот, мы идём по цепочке `next`, находим
свободный слот (обычно в погребе) и связываем его с концом цепочки. Так
получаются «слипающиеся» цепочки — hence *coalesced* hashing. Погреб
отдаляет момент, когда цепочки из разных хеш-адресов начинают
объединяться, и тем самым улучшает производительность поиска.

Размер погреба выбран как `cellar_size = primary_size * (7/43) + 1`.
Это даёт адресный фактор β = primary_size / (primary_size + cellar_size) ≈ **0.86**,
что считается оптимальным для coalesced hashing при различных load factor [1][2].

## Фундаментальные операции

### `_find(key, pos)`

```
pos = hash(key) % primary_size        ← стартовый слот
┌─→ slot = data[pos]
│   если pos == NONE → ключа нет, вернуть NONE
│   если slot.used и slot.key == key → нашли, вернуть pos
│   если slot.used и slot.key != key → идём дальше по цепочке
│   если !slot.used и !slot.deleted  → слот пуст (никогда не занимался) → ключа нет
│   если !slot.used и slot.deleted   → надгробие: пропускаем, идём дальше по цепочке
│   pos = slot.next ─────────────────┘
└─── цикл
```

Ключевой момент: **надгробия** (deleted-слоты) не прерывают поиск. Если элемент
из середины цепочки удалили, `next` сохраняется, и поиск продолжает идти по
цепочке к оставшимся элементам. Пустой (never-used) слот прерывает поиск —
значит, такого ключа в таблице точно нет.

### `_insert(key, value, pos)`

```
1. Если load_factor > 0.5 → rehash (удвоить primary_size)
2. pos = hash(key) % primary_size
3. Если data[pos].used:
   a. Идём по цепочке next, пока не встретили конец (next == NONE)
      или надгробие (deleted == true)
   b. Если остановились на использованном слоте (не надгробие):
      - Сканируем от start_pos вниз, ищем свободный слот
      - Если цепочка слишком длинная (distance > max_lookups) и
        load_factor > 0.25 → rehash и повторить вставку
      - Связываем конец цепочки с найденным свободным слотом:
        data[pos].next = next_free
      - pos = next_free
4. Записываем key, value в data[pos]
   used = True, deleted = False
   (next сохраняем! если вставляем в надгробие — цепочка не рвётся)
5. element_count += 1
```

Важная деталь: при вставке в надгробие (deleted-слот) в середине цепочки,
`next` не сбрасывается. Новый элемент наследует ссылку на продолжение цепочки,
поэтому элементы дальше по цепочке остаются достижимыми.

### `erase(key)`

```
1. pos = find(key, hash(key) % primary_size)
2. Если pos == NONE → ключа нет, вернуть False
3. data[pos].used = False
   data[pos].deleted = True
   (next не трогаем — цепочка должна остаться проходимой)
4. element_count -= 1
```

Слот превращается в надгробие: он больше не «занят», но цепочка через него
проходит. Последующая вставка может переиспользовать этот слот.

## Соответствие операций из условия

| Операция из условия | Метод Python                     |
|---------------------|----------------------------------|
| Вставка элемента    | `__setitem__(key, value)`        |
| Поиск по ключу      | `__getitem__(key)` / `find(key)` |
| Удаление элемента   | `erase(key)`                     |

---

## Асимптотическая сложность

| Операция                       | Амортизированно | Худший случай                    |
|--------------------------------|-----------------|----------------------------------|
| `__setitem__` (вставка)        | O(1)            | O(n) при rehash                  |
| `__getitem__` / `find` (поиск) | O(1)            | O(n) — все ключи в одной цепочке |
| `erase` (удаление)             | O(1)            | O(n) — поиск перед удалением     |

> **Амортизированная O(1)** для вставки гарантируется тем, что rehash
> происходит не чаще, чем каждые O(n) вставок (коэффициент загрузки 0.5),
> а стоимость одного rehash — O(n). В худшем случае (скверная хеш-функция,
> все ключи в одной цепочке) любая операция деградирует до O(n).

## design-решения и почему именно так

### Простые числа для размера таблицы

Размер основной области выбирается из таблицы простых чисел. Это классическая
рекомендация [3][4]: при `size = 2^k` хеш-функция `key % size` фактически
берёт только младшие k бит ключа, и если хеш-функция пользователя плохо
распределяет младшие биты (что бывает нередко), коллизий будет много. Простое
число не имеет нетривиальных делителей, поэтому `key % prime` зависит от
всех бит ключа и распределение получается более равномерным.

### Погреб (cellar) и константа B = 7/43

Coalesced hashing без погреба страдает от того, что цепочки рано
«слипаются»: элемент, вызвавший коллизию в адресе A, может занять слот,
куда потом попытается хешироваться элемент с адресом B, и две цепочки
объединятся. Погреб — это зарезервированная область, куда складываются
только коллизионные элементы. Пока погреб не переполнен, слияния цепочек
не происходит [1][2].

Оптимальный адресный фактор β = M / M' ≈ 0.86, где M — размер адресной
области, M' — полный размер таблицы [1][2]. В данной реализации:

```
cellar_size = primary_size * (7/43) + 1
total_size  = primary_size + cellar_size = primary_size * (50/43) + 1
β           = primary_size / total_size  ≈ 43/50 = 0.86
```

### Надгробия и сохранение ссылок next

При удалении элемента из середины цепочки слот помечается как
`deleted` (надгробие), но ссылка `next` не сбрасывается. Это позволяет
поиску корректно проходить через удалённые элементы. При последующей
вставке в надгробие новый элемент наследует `next`, и цепочка не рвётся.

### Рехеширование при превышении порогов

- **Load factor > 0.5** → удвоение таблицы (preventive rehash).
- **Длина цепочки > max_lookups** при load factor > 0.25 → экстренный
  rehash. Это страховка от скверных хеш-функций, которые создают
  длинные цепочки даже при низкой загрузке.

`max_lookups` ≈ ⌈log₂(primary_size)⌉ — эвристика: цепочка длиннее
логарифма от размера таблицы — повод насторожиться.

## Использование

```python
h = HashMap()
h["apple"] = 1
h["banana"] = 2

print(h["apple"])  # 1         (__getitem__)
print(h.find("banana"))  # 2   (find)
print("cherry" in h)  # False  (__contains__)

h.erase("apple")
print(h.size())  # 1
```
